# Binary Number Game

The main idea is to create a binary number game where users convert dotted decimal notation numbers to binary. The underlying goal is to help the users learn to convert from base 10 to base 2 in a fast and effecient way. The target audience will be aspiring network technicians studying for exams like the CCNA where you are expected to be able to convert an IP address to binary. So, the main number that will be converted will be IP addresses like 192.168.01 and 10.10.10.10, basically any type of IP4 Address.

The most important goal is to make the game multiplayer friendly. I am thinking 1 vs 1 where both players compete to solve the conversion first. Once a player succesfully completes the sequence, a new number to convert is generated by the game.

This document is the full design spec intended for an AI coding agent to implement the game from. It should be treated as the source of truth for architecture, gameplay rules, visuals, and networking behavior.

## Tech Stack Recommendation

- **Backend:** Python with FastAPI (or Flask + Flask-SocketIO). FastAPI is preferred because it has native `WebSocket` support without extra dependencies, and pairs well with `uvicorn` for an async server that can handle many concurrent multiplayer connections.
- **Realtime layer:** Native WebSockets (`/ws/multiplayer/{room_id}`) rather than long-polling, since low latency matters for a head-to-head speed game.
- **Frontend:** Plain HTML5, CSS3, and vanilla JavaScript (ES modules). No heavy framework is required — the UI surface is small (menu, game board, HUD) and a framework would add build-step overhead. Keep JS organized into modules: `game.js` (core loop/state), `ui.js` (DOM rendering + animations), `network.js` (WebSocket client), `audio.js` (sound effects), `scoring.js`.
- **Persistence:** Start with in-memory state on the server for active matches (a dict keyed by room id). Optionally add SQLite later for leaderboards/high scores — not required for MVP.
- **Static file serving:** FastAPI can serve the `static/` folder directly for local dev; no separate frontend build tool needed (no bundler required, keep it dependency-light).

## Game Rules

There should be three modes: "Free Play", "Timed Play", and "Multiplayer"

**Free Play** - the user can play at their own pace.

**Timed Play** - the user only has x amount of seconds to convert the entire IP address (we may tweak this later, but start with 60 seconds)

**Multiplayer** - two users are matched up against one another and most solve the same IP before the other user.

General gameplay should consist of solving one IP address at a time. Once one is solved, another is generated. The user types in the answer, then there is a button that say "Submit" to check the answer.

### IP Address Generation

- Generate a random valid IPv4 address, one octet (0-255) at a time, as four separate decimal values.
- Avoid repeating the same IP twice in a row within a single session.
- Difficulty can optionally scale over time (e.g. after N correct answers, start biasing toward octets with more `1` bits, which are harder to convert quickly) — this is a stretch goal, not required for MVP.
- The same generation function/logic should be shared (or mirrored) between the server (for multiplayer, where the server is authoritative) and the client (for free play / timed play, which can run fully client-side with no server round trip needed).

### Answer Submission & Validation

- Each octet's binary answer is exactly 8 characters (0s and 1s only). Input fields should reject/ignore non-binary characters as they're typed.
- The "Submit" button checks all four octets at once.
- Validation is per-octet: each of the 4 chunks is graded independently correct/incorrect.
- Pressing Enter should behave the same as clicking Submit.

### Scoring

- **Free Play:** flat points per correctly solved IP address (e.g. 100 points), no time pressure.
- **Timed Play:** points scale with speed — e.g. base points + a bonus that decays the longer the player takes within the 60-second window (for example: `points = base_points + max(0, (time_remaining_when_solved / total_time) * bonus_pool)`).
- **Streak bonus:** for every X correct IPs in a row (e.g. every 5), award a flat streak bonus on top of normal scoring.
- **Progressive multiplier:** starts at 1x. Every X correct answers in a row (e.g. every 5 correct) bumps the multiplier to the next tier: 2x, 4x, 8x, 16x, 32x, 64x, 128x. All points earned (base + streak bonus) are multiplied by the current multiplier. A single wrong/incorrect submission resets the multiplier back to 1x and resets the streak counter. This system applies identically to Free Play and Timed Play.
- **Multiplayer:** scoring is secondary to speed (first to solve the round wins the round), but the same base/streak/multiplier system can still track an overall score across rounds within a match, used as a tiebreaker or bragging-rights stat at the end of the match.

### Retry / Reveal Flow (Free Play & Timed Play only)

- On an incorrect submission, only the incorrect chunk(s) are cleared; correct chunks keep their values (see Animations). The player can retry immediately.
- After 2 failed attempts on the same IP, show a "Reveal Answer" button/link next to Submit. Clicking it fills in the correct answer, plays no correct-answer sound (since it wasn't earned), awards 0 points for that IP, resets the streak/multiplier, and immediately advances to the next IP.
- This reveal option is **not available in Multiplayer** — players must solve it themselves or lose the round.

Each IP address should be in four chuncks, with each chunk being its own box, with rounded corners. Under that should be where the user enters their answer, it should be matching boxes for each of the four sections as well.

If the user's answer is correct, the boxes should flash blue and bounce up and down slighty. If wrong, they should flash red and shake side to side slightly. If one chunk is wrong, only that chunk should flash red and shake, the right ones blue and bounce. Keep their answer inside the chunk if it is correct, if not, clear the chunk that was wrong (that way they don't have to reenter what they got correct).

 (The top row should have the exponents as well)

When a game first starts, there should be a 3 2 1 countdown, then "GO!"

### Animation Details

Use CSS animations/transitions (via `@keyframes` + toggled classes) driven by JS, rather than a JS animation library — this keeps things GPU-accelerated and dependency-free.

**Feedback pass (on Submit):**
1. For each of the 4 chunks, add a class based on result: `.chunk--correct` or `.chunk--incorrect`.
2. `.chunk--correct`: flashes blue glow (`box-shadow`/`background-color` transition, ~150-200ms) and plays a "bounce" keyframe animation (translateY up/down, e.g. `0 → -8px → 0`, ease-out, ~400ms, 1-2 bounces).
3. `.chunk--incorrect`: flashes red glow and plays a "shake" keyframe animation (translateX left/right, e.g. `0 → -6px → 6px → -4px → 4px → 0`, ~400ms).
4. After the feedback animation completes (`animationend` event, not a fixed `setTimeout` where avoidable), incorrect chunks are cleared (input reset to empty, focus returned to the first incorrect chunk) while correct chunks retain their value and lock (read-only) until the round fully clears.

**Round-clear "fall away" sequence (once all 4 chunks are correct):**
1. All 4 chunks briefly flash blue in unison (confirms full match).
2. Each answer chunk plays a "fall" keyframe: `transform: translateY(0) → translateY(120%)` combined with `opacity: 1 → 0` and a slight rotation for flair (e.g. `rotate(6deg)` on odd chunks, `-6deg` on even chunks), staggered by ~80-100ms per chunk (left to right) using `animation-delay`.
3. Simultaneously (or with a slight delay after fall starts), the reference/question row's 4 new chunks animate in from above: `transform: translateY(-120%) → translateY(0)`, `opacity: 0 → 1`, also staggered left to right, using an ease-in-out or a slight bounce/overshoot easing (`cubic-bezier(0.34, 1.56, 0.64, 1)`) so they feel like they "drop into place."
4. Once the new question chunks land, the 4 answer input boxes reset to empty and unlock, ready for input.
5. Total round-clear transition should be brisk — target ~500-700ms total — so it doesn't slow down competitive/timed play.

**Countdown sequence (game start):**
1. Overlay covers the play area with "3", pause ~700-800ms, scale/fade transition to "2", then "1", then "GO!" (GO! can have a punchier scale-in/scale-out and a distinct color, e.g. the blue accent).
2. Timer (Timed Play) and opponent sync (Multiplayer) only start counting once "GO!" finishes.
3. Reuse the same countdown component across all three modes for consistency.

**Pause behavior:**
1. Clicking Pause immediately blurs/hides the reference chart, the current IP chunks, and the answer inputs (e.g. swap in a "Paused" overlay panel, or apply a CSS `filter: blur(12px)` + `pointer-events: none` to the play area).
2. Timed Play: the countdown timer stops accumulating while paused.
3. Multiplayer: pausing does **not** stop the opponent's or the match clock — instead it opens a confirmation modal ("Quit to Main Menu? You will forfeit this match.") rather than a true pause, since pausing a live head-to-head match isn't fair to the opponent. Free Play and Timed Play get a real pause; Multiplayer's "pause" button is effectively a "quit/forfeit" prompt.

### Main Menu

The game should start at the main menu, with a couple options:

1. Free Play
2. Timed Play
3. Multiplayer

Additional main menu considerations:
- A short player name/handle prompt (stored in `localStorage`) should be captured before entering Multiplayer, so opponents can be identified in the UI.
- Multiplayer selection transitions to a "Finding opponent..." waiting screen (see Multiplayer Implementation) with a cancel/back option.
- Keep the reference power-of-two chart visible/accessible from the menu too (e.g. as a small "How to Play" link) so new players can learn the mechanic before jumping in.

### Sound

Typing in an answer should make a clicky keyboard sound with each click.

Correct answer should also give a cling sound, while a wrong answer makes a buzz sound.

Additional sound considerations:
- Play the per-chunk key click sound on every valid keypress (0 or 1) into an input box; ignore/do not play it for rejected invalid characters.
- Correct-chunk "cling" and incorrect-chunk "buzz" sounds should play immediately when the Submit feedback pass begins (in sync with the flash/bounce/shake animations starting), not after they finish.
- Play a distinct short chime on the full round-clear ("fall away") sequence, separate from the individual correct-chunk cling, so players get a clear sense of "IP fully solved."
- Countdown "3, 2, 1" should each tick with a short beep, and "GO!" should have its own more energetic sound.
- Provide a mute/volume toggle in the UI (persisted in `localStorage`) — some players will want the game silent.
- Use the Web Audio API or simple `<audio>` elements with cloned nodes per play (so rapid typing doesn't cut off overlapping click sounds).

## Multiplayer Implementation

### Overview

Multiplayer is 1v1, synchronous, and round-based: both players see the **same** randomly generated IP address at the same time, and race to be the first to correctly submit all 4 octets. Whoever solves it first wins that round and scores a point; the server then immediately generates and broadcasts the next IP to both players. A match ends after a fixed number of rounds (e.g. first to 5 round-wins) or a fixed match timer (e.g. 3 minutes), whichever the game design settles on — recommend **first to 5 round wins** for a clean, decisive MVP.

### Architecture

- The **server is authoritative**: it owns the current IP address for the match, validates submissions, decides who "won" the round (based on which valid submission arrives first), and broadcasts round-clear/next-IP events. This prevents client-side cheating (e.g. a modified client claiming a false "correct" answer) and avoids desync between the two players.
- Communication is via **WebSockets**, one connection per player, both joined to a shared "room" (match) identified by a room id.
- Free Play and Timed Play remain fully client-side (no server dependency) since there's no opponent to stay in sync with.

### Matchmaking Flow

1. Player selects "Multiplayer" on the main menu → client opens a WebSocket to `/ws/matchmaking` and sends a `join_queue` message with their player name.
2. Server holds a simple FIFO queue of waiting players (in-memory list). When 2 players are queued, the server pairs them, creates a `Match` object with a new `room_id`, and sends both clients a `match_found` message containing the room id and opponent's name.
3. Both clients then open (or are redirected to) a WebSocket connection scoped to `/ws/match/{room_id}`.
4. Server waits for both players' sockets to report "ready" (i.e. connected and loaded), then broadcasts `countdown_start` to both simultaneously so the 3-2-1-GO countdown is synchronized.
5. If a player disconnects/cancels while queued, remove them from the queue. If a player disconnects mid-match, the server should broadcast an `opponent_disconnected` event to the remaining player after a short grace period (e.g. 10 seconds for reconnect), and if they don't reconnect, award the remaining player a win by forfeit.

### In-Match Protocol (WebSocket message types)

Client → Server:
- `join_queue { player_name }`
- `ready { room_id }` — client finished loading the match screen
- `submit_answer { room_id, octets: [str, str, str, str] }`
- `leave_match { room_id }` — quit/forfeit

Server → Client:
- `match_found { room_id, opponent_name }`
- `countdown_start { server_time }`
- `round_start { ip_octets_masked_for_display, round_number }` — server sends the target IP's *decimal* octets (players still convert it themselves; the server never sends the binary answer)
- `submission_result { correct_per_octet: [bool,bool,bool,bool] }` — sent back to the *submitting* player only, so their local UI can animate correct/incorrect chunks
- `round_won { winner_name, round_number, scores }` — broadcast to both players when someone gets all 4 octets correct first
- `next_round { ip_octets, round_number }` — broadcast shortly after `round_won`, following the same fall-away/new-chunk animation as single-player
- `match_over { winner_name, final_scores }`
- `opponent_disconnected`, `opponent_reconnected`

### Fairness / Anti-Cheat Notes

- Never send the correct binary answer to the client; only send correct/incorrect per octet.
- The server should timestamp each `submit_answer` server-side (not trust client-reported timing) so round-winner determination is based on server receive order.
- Rate-limit `submit_answer` messages per player (e.g. max 1 per 200ms) to prevent spamming random guesses as a brute-force strategy.
- Both players should be shown the exact same IP per round — generate it once server-side and broadcast it, never generate independently per client.

### Reconnection Handling

- Give each player a short-lived session token (e.g. a UUID stored in `sessionStorage`) when a match starts, so a page refresh/brief network drop can rejoin the same `room_id` and resume rather than being treated as a new player.

## Data Model Sketch (for `models.py`)

```python
@dataclass
class Player:
    id: str
    name: str
    websocket: WebSocket | None

@dataclass
class RoundResult:
    round_number: int
    ip_octets: tuple[int, int, int, int]
    winner_id: str | None
    started_at: float
    ended_at: float | None

@dataclass
class Match:
    room_id: str
    players: list[Player]           # exactly 2
    rounds: list[RoundResult]
    scores: dict[str, int]          # player_id -> round wins
    status: str                     # "waiting" | "countdown" | "in_progress" | "finished"
```
